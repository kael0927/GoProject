## Go Channel 阻塞机制与死锁核心笔记

## 一、阻塞机制核心

- **发送阻塞**：无缓冲 Channel 无接收者；有缓冲 Channel 已满。
- **接收阻塞**：Channel 无数据且无发送者。
- **本质**：Goroutine 挂起（Gwaiting），调度器移交 P 给其他协程，避免 CPU 空转。

## 二、Channel 是“水管”不是“水池”

- 核心价值：数据流动，边写边读。
- 静态存储 = 水池；持续流动 = 水管。

## 三、三种读写速率场景

| 场景 | 结果 | 原因 |
|:---|:---|:---|
| 只写不读 | **死锁** | 缓冲区满后写入者永久阻塞，无人唤醒 |
| 写快读慢 | 正常 | 缓冲区满则写阻塞，读后自动唤醒 |
| 写慢读快 | 正常 | 缓冲区空则读阻塞，写后自动唤醒 |

## 四、死锁判定

- **条件**：所有 Goroutine 阻塞，且无任何 Goroutine 可被唤醒。
- **典型场景**：
  - 只写不读
  - 只读不写
  - 无缓冲 Channel 双向等待
  - 主协程取空 Channel
- **隐式死锁**：无缓冲双向等待，Go 运行时无法检测，程序静默挂起。

## 五、Channel 使用六注意

1. 只能存放声明时指定的类型。
2. 容量满后不能再写入。
3. 取出数据后可继续写入。
4. 无协程时取空会报 `deadlock`。
5. 关闭后只能读，不能再写。
6. `for range` 遍历未关闭 Channel 会阻塞（`deadlock`）。

## 六、避免死锁方案

- 确保有写有读。
- 使用缓冲 Channel。
- 写入完成后及时 `close()`，让 `for range` 正常退出。
- 使用 `select` + `default` 避免永久阻塞。

## Go Channel 核心使用细节

## 一、4 项核心使用规则

### 1. 数据类型约束
- channel 只能存放声明时指定的数据类型，类型不匹配编译器直接报错
- 例：声明为 `chan int` 的管道，存入 `10.9` 浮点数会报 `constant 10.9 truncated` 错误

### 2. 满存阻塞死锁
- 容量已满的 channel 继续写入数据，会触发死锁（`fatal error: all goroutines are asleep`）
- 只要从 channel 中取出任意一个数据，释放出一个位置，就可以继续写入
- **设计本质**：channel 是“水管”不是“水池”——核心价值是让数据流动起来，一边写一边读，而非静态存储

### 3. 取空报错规则
- 在没有使用协程的场景下，从已经取空的 channel 中继续执行取出操作，程序会抛出运行时错误
- 有协程配合时，取空操作会阻塞等待，不会直接报错

### 4. 无变量接收取出
- 从 channel 取数据时，可以不使用变量接收，直接将取出内容丢弃（`<-ch`）
- 该操作仍属于合法的取出动作，同样会释放一个写入名额
- **典型用途**：跳过前面的元素、清理管道

## 二、6 类实操场景

| 序号 | 场景 | 关键要点 |
|:---:|:---|:---|
| 1 | 基础类型（int） | 先进先出队列特性，按写入顺序依次取出 |
| 2 | map 类型 | 存入前必须先用 `make` 初始化 map，否则报错；每个元素是独立的 map，内含多组 k-v |
| 3 | 结构体类型 | 用法与基础类型完全一致，直接写入和取出结构体实例 |
| 4 | 指针类型 | channel 原生支持存放指针，可避免大体积结构体的拷贝开销，提升效率 |
| 5 | 空接口混合类型 | 声明为 `chan interface{}` 即可存放任意类型；严格遵循先进先出，无法随机访问 |
| 6 | 空接口取结构体字段 | 直接 `.字段名` 编译报错，必须用**类型断言**转换后才能访问字段 |

## 三、重点难点：空接口 channel 与类型断言

### 报错现象
向 `chan interface{}` 写入结构体实例后，取出时虽然运行时能打印出结构体类型和值，但**编译阶段**直接通过 `.name` 访问字段会报错：

```
type interface {} is interface with no methods
```

### 底层原理
- **编译阶段**：编译器只知道取出的变量是 `interface{}` 类型，空接口没有任何字段定义，因此找不到 `.name`
- **运行阶段**：程序运行时才动态识别出底层存储的真实结构体类型
- 静态类型与动态类型分离，是 Go 语言接口机制的核心特性

### 解决方案：类型断言
```go
newCat := <-allChannel
a := newCat.(cat)  // 类型断言，手动告知编译器真实类型
fmt.Println(a.name) // 正常访问字段
```

## 四、补充技巧

- **跳过元素**：想取第 N 个元素，必须先执行 N-1 次无变量接收的取出操作，将前面的元素丢弃
- **流动思维**：channel 的设计初衷是协程间通讯，边写边读才是常态，不要把它当静态容器用
- **指针优先**：存放大结构体时，优先使用指针类型的 channel，减少值拷贝开销

### 📝 Go 并发实战笔记：阶乘计算与全局互斥锁解决资源竞争
#### 🎯 一、 实战需求与暴露的问题
- 需求：并发计算 1~200 的阶乘，存入一个全局 map，最后主线程遍历打印。
   初版代码逻辑：
- 定义全局 myMap。
- 写 test(n) 函数，计算 n 的阶乘并写入 myMap。
- main 中 for 循环启动 200 个协程 go test(i)，随后遍历 myMap。
- 跑起来后，遭遇了三个致命问题：
- 主线程提前退出：程序瞬间结束，没有任何输出。因为主线程不会等待子协程，一旦主线程结束，未执行完的协程会被直接杀死。 
- 并发写 Map 崩溃：加上 time.Sleep 等待后，程序直接抛出致命错误 fatal error: concurrent map writes。因为 Go 原生 - map 不是并发安全的，多个协程同时写入会直接崩溃。
- 加锁不彻底，底层仍报错：在写操作处加了锁，但 go build -race 检测依然报 data race 错误。因为主线程读 map 时没有加锁。

### 二、 核心问题解答
- 1.加锁的作用？何时加锁：
  - 作用：将“并发操作”强制变成“排队操作”。防止多个协程同时修改同一块内存（资源竞争），避免数据错乱或程序崩溃。
   - 何时加锁：
   - 写操作：必然要加锁（多个协程同时写直接导致 fatal error）。
   - 读操作：也要加锁。哪怕你主观上知道主线程休眠10秒后所有子协程早已写入完毕，但 Go 底层运行时不知道你休眠了多久。       只要检测到“读”和“潜在的写”有可能同时发生，就会判定为资源竞争（data race）。
   - 口诀：访问共享资源前 Lock()，访问完毕后立刻 Unlock()，推荐用 defer lock.Unlock() 防死锁。
- 2.全局互斥锁的作用？
   - 什么是全局：在包级别声明 var lock sync.Mutex。所有协程共享同一把锁。
   - 作用：保证在同一时刻，只有一个协程能进入被保护的代码区（临界区）。
   - 为什么必须是全局：如果每个协程在自己的函数内部定义 var lock sync.Mutex，那就是各锁各的，完全起不到互斥作用。
   - 生活类比（排队上厕所）：共享 map 是唯一的厕所坑位，全局互斥锁就是门锁。第一个人进去反锁门，后面的人必须在门外排队；前一- 个人出来释放锁，队首的下一个人才能进去。
- 3.通过此案例，如何加深理解教学内容？
   - 这个案例完美演示了并发编程的“发现问题 -> 临时补救 -> 彻底解决 -> 遇到新坑”的完整闭环：
   - 时序问题：不能用 time.Sleep 盲猜等待时间，应用 sync.WaitGroup 精准等待。
   - 安全边界：读和写共享资源都必须纳入锁的保护范围。
   - 排错工具：学会使用 go build -race 精准定位竞争位置。


### 一、进程与线程

### 1.1 进程（Process）

**定义**：进程是程序在操作系统中的一次执行过程，是系统进行**资源分配和调度的基本单位**。

**特性**：

- 双击运行磁盘上的 `.exe` 文件 → 调入内存 → 成为一个进程（可在任务管理器中查看，如 notepad、Word）
- 重量级：启动后占用大量系统资源（如迅雷）
- 关闭进程 → 对应程序界面同步消失
- 一个程序能否启动多个进程，由程序本身的设计逻辑和操作系统规则共同决定（如早期暴风影音可多开，后优化为单实例）

### 1.2 线程（Thread）

**定义**：线程是进程的执行实例，是**程序执行的最小单位**，资源占用量远小于进程。

**实例**：迅雷进程中，每一个正在下载的文件对应一个独立线程；可同时下载线程数可自定义（常见 5~10 个）。

### 1.3 三者层级关系

```javascript
程序（磁盘上的 exe 文件）
  └── 进程（双击运行后被调入内存；至少 1 个）
        └── 线程（进程内部；至少 1 个，可创建销毁多个，同一进程内多个线程并发执行）
```

## 二、并发与并行

|  | 并发（Concurrency） | 并行（Parallelism） |
| --- | --- | --- |
| **硬件环境** | 单核 CPU | 多核 CPU |
| **微观执行** | 同一时间点只有 1 个任务在执行，CPU 以毫秒级时间片快速轮巡切换 | 同一时间点多个任务在不同核心上同时执行 |
| **宏观感知** | 人类无法感知毫秒级切换，误以为多个任务同时运行 | 真正的同时运行 |
| **例子** | 单核设备同时开两个视频网页，实际在轮巡切换 | 10 个线程在 10 核 CPU 上各占一核 |
| **速度** | 受切换开销限制 | 远高于并发，充分释放多核算力 |

**场景对比**：10 个线程各执行 10ms——

- 并发（单核）：逐个轮巡，微观任意时刻仅 1 个线程执行
- 并行（10 核）：每线程独占一个核心，微观上全部同步执行

## 三、Go 协程（goroutine）与主线程

### 3.1 技术演进脉络

```javascript
早期：单进程单任务 → 效率极低
  ↓
线程：轻量级进程，初步实现并发能力
  ↓
Go 协程：汤普森团队的两大设计目标
  ① 让 8 核 CPU 的所有核心都参与运算
  ② 解决传统线程资源占用过高的问题
```

**行业规律**：硬件的发展速度始终快于软件的发展速度。

### 3.2 协程的核心定位

> 协程可以直接理解为**轻量级的线程**，多个协程之间共享底层线程的公共资源。

- Go 可轻松稳定运行**上万个协程**同时工作，传统线程难以做到
- 协程完全设计为逻辑态，在编译器和调度算法层面做了大量优化，大幅降低 CPU 和内存占用

### 3.3 Go 主线程（命名注意）

- Go 程序运行必然依赖操作系统进程，只是日常开发习惯称"主线程"
- Go 的主线程在概念上等效于传统语言中的进程/普通线程（社区命名不完全统一，读书时留意不同作者的表述差异）
- 关系：单条主线程内部可以运行**大量协程**（承载与被承载的关系）

### 3.4 协程的四大核心特点（面试必背）

1. 每个协程拥有**独立的栈空间**，不同协程的栈数据相互独立，不会冲突
2. 所有协程**共享程序的堆空间**，可通过堆空间实现数据交互
3. 协程的调度**完全由用户程序控制**，开发者可自主决定协程的开启和终止时机（不需要操作系统介入）
4. 协程是**轻量级执行单元**，资源占用远低于进程和线程

# 📁 测试文件和函数怎么写才合规？

命名有强制后缀 + 首字母大写两条硬规则，写错会直接导致用例不执行。

- **文件命名**：必须以 `_test.go` 结尾；前缀无强制要求；测试文件不参与常规编译打包，仅执行 `go test` 时加载。
- **函数命名**：必须以大写 `Test` 开头；小写 `test` 开头会被框架直接忽略（IDE 可能提示波浪线）。推荐 `Test + 被测函数名` 格式，方便团队识别。
- **入参固定**：测试函数形参必须是 `*testing.T` 类型，这是 Go 测试框架的核心上下文对象。
- **多函数共存**：单个 `_test.go` 文件内可定义多个测试用例函数，互不影响。

# 🔧 testing.T 最常用的 API 有哪些？

日常开发 `Errorf` 和 `Logf` 使用频率最高，覆盖错误输出和日志记录两个核心场景。

- **Errorf**：格式化输出错误信息，标记用例失败但**继续执行**。
- **Logf**：格式化输出运行日志，仅 `-v` 模式或用例失败时显示。
- **FailNow / Fatalf**：**立即终止**当前测试用例，用于致命错误场景。
- **其他方法**：还包含 `Run`（子测试）、`Skip`（跳过用例）等，可按需查阅官方文档。

# ⚙️ go test 指令怎么精准控制运行范围？

通过参数组合可实现全量运行、单文件运行、单函数运行三种粒度，大幅提升调试效率。

| 运行场景 | 指令格式 | 关键特性 |
|:---|:---|:---|
| 全量测试 | `go test -v` | 扫描当前目录所有测试文件 |
| 单文件测试 | `go test -v 测试文件.go 原文件.go` | 需同时指定被测试原文件，否则报 `undefined` |
| 单函数测试 | `go test -v -run 函数名` | 严格区分大小写，写错返回 `no test to run` |

- **`-v` 参数**：加 `-v` 输出完整运行日志；不加则仅显示最终结果，通过用例的日志会被隐藏，失败用例的错误信息仍会正常输出。
- **结果标识**：`pass` 表示全部用例通过，`fail` 表示至少一个用例失败，失败时会精准定位到出错代码行号。

# 💡 容易踩的坑有哪些？

三个新手高频出错点，记住能省大量排查时间。

- **大小写敏感**：测试函数首字母、`-run` 参数匹配都严格区分大小写，写错会导致用例不被识别。
- **编译隔离**：测试代码不会混入生产包，不需要额外配置构建标签，这是 Go 原生测试的独特优势。
- **单文件依赖**：指定单个测试文件运行时，必须同时带上被测试的原文件，否则会因找不到依赖报错。

## 四、init() 函数

### 4.1 作用

导入包时，若存在 `init()` 函数，**先执行 `init()`，再执行 `main()`**。一般用于初始化包中所需的数据。

### 4.2 执行顺序

| 场景 | 执行顺序 |
|:---|:---|
| 同一个 `.go` 文件 | 从上到下 |
| 同一个 `package` 的多个 `.go` 文件 | 按**文件名字符串排序** |
| 不同包（无互相依赖） | 按 `main` 包中 `import` 的书写顺序 |
| 不同包（存在依赖） | **最后被依赖的最先执行** |

## 五、注意事项

| 类型 | 内容 |
|:---|:---|
| ❌ 循环依赖 | `a` 依赖 `b`，`b` 依赖 `c`，`c` 又依赖 `a` → 死循环，编译报错 |
| ✅ 单次初始化 | 一个包可被多个包导入，但**只初始化一次** |

| 知识点 | 核心内容 |
|:---|:---|
| 包的本质 | 目录 |
| 包名规范 | 与目录名一致 |
| 可见性 | 首字母大写 = 导出（公共） |
| `init()` 执行时机 | `main()` 之前 |
| 同文件 `init` 顺序 | 从上到下 |
| 同包多文件 `init` 顺序 | 按文件名字符串排序 |

| 包初始化次数 | 仅一次 |
