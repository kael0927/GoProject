## 一、进程与线程

### 1.1 进程（Process）

**定义**：进程是程序在操作系统中的一次执行过程，是系统进行**资源分配和调度的基本单位**。

**特性**：

- 双击运行磁盘上的 `.exe` 文件 → 调入内存 → 成为一个进程（可在任务管理器中查看，如 notepad、Word）
- 重量级：启动后占用大量系统资源（如迅雷）
- 关闭进程 → 对应程序界面同步消失
- 一个程序能否启动多个进程，由程序本身的设计逻辑和操作系统规则共同决定（如早期暴风影音可多开，后优化为单实例）

### 1.2 线程（Thread）

**定义**：线程是进程的执行实例，是**程序执行的最小单位**，资源占用量远小于进程。

**实例**：迅雷进程中，每一个正在下载的文件对应一个独立线程；可同时下载线程数可自定义（常见 5~10 个）。

### 1.3 三者层级关系

```javascript
程序（磁盘上的 exe 文件）
  └── 进程（双击运行后被调入内存；至少 1 个）
        └── 线程（进程内部；至少 1 个，可创建销毁多个，同一进程内多个线程并发执行）
```

## 二、并发与并行

|  | 并发（Concurrency） | 并行（Parallelism） |
| --- | --- | --- |
| **硬件环境** | 单核 CPU | 多核 CPU |
| **微观执行** | 同一时间点只有 1 个任务在执行，CPU 以毫秒级时间片快速轮巡切换 | 同一时间点多个任务在不同核心上同时执行 |
| **宏观感知** | 人类无法感知毫秒级切换，误以为多个任务同时运行 | 真正的同时运行 |
| **例子** | 单核设备同时开两个视频网页，实际在轮巡切换 | 10 个线程在 10 核 CPU 上各占一核 |
| **速度** | 受切换开销限制 | 远高于并发，充分释放多核算力 |

**场景对比**：10 个线程各执行 10ms——

- 并发（单核）：逐个轮巡，微观任意时刻仅 1 个线程执行
- 并行（10 核）：每线程独占一个核心，微观上全部同步执行

## 三、Go 协程（goroutine）与主线程

### 3.1 技术演进脉络

```javascript
早期：单进程单任务 → 效率极低
  ↓
线程：轻量级进程，初步实现并发能力
  ↓
Go 协程：汤普森团队的两大设计目标
  ① 让 8 核 CPU 的所有核心都参与运算
  ② 解决传统线程资源占用过高的问题
```

**行业规律**：硬件的发展速度始终快于软件的发展速度。

### 3.2 协程的核心定位

> 协程可以直接理解为**轻量级的线程**，多个协程之间共享底层线程的公共资源。

- Go 可轻松稳定运行**上万个协程**同时工作，传统线程难以做到
- 协程完全设计为逻辑态，在编译器和调度算法层面做了大量优化，大幅降低 CPU 和内存占用

### 3.3 Go 主线程（命名注意）

- Go 程序运行必然依赖操作系统进程，只是日常开发习惯称"主线程"
- Go 的主线程在概念上等效于传统语言中的进程/普通线程（社区命名不完全统一，读书时留意不同作者的表述差异）
- 关系：单条主线程内部可以运行**大量协程**（承载与被承载的关系）

### 3.4 协程的四大核心特点（面试必背）

1. 每个协程拥有**独立的栈空间**，不同协程的栈数据相互独立，不会冲突
2. 所有协程**共享程序的堆空间**，可通过堆空间实现数据交互
3. 协程的调度**完全由用户程序控制**，开发者可自主决定协程的开启和终止时机（不需要操作系统介入）
4. 协程是**轻量级执行单元**，资源占用远低于进程和线程

# 📁 测试文件和函数怎么写才合规？

命名有强制后缀 + 首字母大写两条硬规则，写错会直接导致用例不执行。

- **文件命名**：必须以 `_test.go` 结尾；前缀无强制要求；测试文件不参与常规编译打包，仅执行 `go test` 时加载。
- **函数命名**：必须以大写 `Test` 开头；小写 `test` 开头会被框架直接忽略（IDE 可能提示波浪线）。推荐 `Test + 被测函数名` 格式，方便团队识别。
- **入参固定**：测试函数形参必须是 `*testing.T` 类型，这是 Go 测试框架的核心上下文对象。
- **多函数共存**：单个 `_test.go` 文件内可定义多个测试用例函数，互不影响。

# 🔧 testing.T 最常用的 API 有哪些？

日常开发 `Errorf` 和 `Logf` 使用频率最高，覆盖错误输出和日志记录两个核心场景。

- **Errorf**：格式化输出错误信息，标记用例失败但**继续执行**。
- **Logf**：格式化输出运行日志，仅 `-v` 模式或用例失败时显示。
- **FailNow / Fatalf**：**立即终止**当前测试用例，用于致命错误场景。
- **其他方法**：还包含 `Run`（子测试）、`Skip`（跳过用例）等，可按需查阅官方文档。

# ⚙️ go test 指令怎么精准控制运行范围？

通过参数组合可实现全量运行、单文件运行、单函数运行三种粒度，大幅提升调试效率。

| 运行场景 | 指令格式 | 关键特性 |
|:---|:---|:---|
| 全量测试 | `go test -v` | 扫描当前目录所有测试文件 |
| 单文件测试 | `go test -v 测试文件.go 原文件.go` | 需同时指定被测试原文件，否则报 `undefined` |
| 单函数测试 | `go test -v -run 函数名` | 严格区分大小写，写错返回 `no test to run` |

- **`-v` 参数**：加 `-v` 输出完整运行日志；不加则仅显示最终结果，通过用例的日志会被隐藏，失败用例的错误信息仍会正常输出。
- **结果标识**：`pass` 表示全部用例通过，`fail` 表示至少一个用例失败，失败时会精准定位到出错代码行号。

# 💡 容易踩的坑有哪些？

三个新手高频出错点，记住能省大量排查时间。

- **大小写敏感**：测试函数首字母、`-run` 参数匹配都严格区分大小写，写错会导致用例不被识别。
- **编译隔离**：测试代码不会混入生产包，不需要额外配置构建标签，这是 Go 原生测试的独特优势。
- **单文件依赖**：指定单个测试文件运行时，必须同时带上被测试的原文件，否则会因找不到依赖报错。

## 一、包的基本概念

| 序号 | 规则 |
|:--:|:---|
| 1 | 一个目录下的所有 `.go` 文件归属同一个包，`package` 声明必须一致 |
| 2 | `package` 声明的包名与对应的目录名**习惯上保持一致** |
| 3 | 包可以嵌套（目录下可以有子目录/子包） |
| 4 | 同包下的函数不需要导入包，直接调用 |
| 5 | `main` 包是 `main()` 函数所在的包，**其他包不能使用 `package main`** |
| 6 | 导入路径 = 模块名 + 从项目根目录到该文件夹的完整路径（用 `/` 分隔） |
| 7 | **包的本质就是一个目录** |

## 二、包的声明与导入

```go
// 声明
package utils

// 导入
import "myproject/utils"
```

## 三、包的可见性

- **首字母大写** → 可被导出（公共的，其他包可访问）
- **首字母小写** → 包内私有（其他包不可访问）

> 💡 记忆口诀：大写公开，小写私有。

## 四、init() 函数

### 4.1 作用

导入包时，若存在 `init()` 函数，**先执行 `init()`，再执行 `main()`**。一般用于初始化包中所需的数据。

### 4.2 执行顺序

| 场景 | 执行顺序 |
|:---|:---|
| 同一个 `.go` 文件 | 从上到下 |
| 同一个 `package` 的多个 `.go` 文件 | 按**文件名字符串排序** |
| 不同包（无互相依赖） | 按 `main` 包中 `import` 的书写顺序 |
| 不同包（存在依赖） | **最后被依赖的最先执行** |

## 五、注意事项

| 类型 | 内容 |
|:---|:---|
| ❌ 循环依赖 | `a` 依赖 `b`，`b` 依赖 `c`，`c` 又依赖 `a` → 死循环，编译报错 |
| ✅ 单次初始化 | 一个包可被多个包导入，但**只初始化一次** |

## 六、速查表

| 知识点 | 核心内容 |
|:---|:---|
| 包的本质 | 目录 |
| 包名规范 | 与目录名一致 |
| 可见性 | 首字母大写 = 导出（公共） |
| `init()` 执行时机 | `main()` 之前 |
| 同文件 `init` 顺序 | 从上到下 |
| 同包多文件 `init` 顺序 | 按文件名字符串排序 |
| 无依赖包 `init` 顺序 | 按 `import` 顺序 |
| 有依赖包 `init` 顺序 | 最后被依赖的先执行 |
| 循环依赖 | ❌ 禁止 |
| 包初始化次数 | 仅一次 |

> 📝 **总结**：理解包的目录本质、可见性规则和 `init()` 的执行顺序，是写出规范 Go 代码的基础。特别注意**循环依赖的避免**和**依赖包的初始化顺序**。
